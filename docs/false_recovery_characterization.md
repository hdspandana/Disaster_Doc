# False-Recovery Characterization

**Phase:** controlled characterization only  
**Status:** complete; no classifier or production-rule changes made

## Purpose and scope

This phase measures how the existing deterministic `classify_field` rules respond to a small, deliberately constructed set of OCR-like strings. It is a characterization of the **current classifier**, not a benchmark of EasyOCR or a claim about real documents.

The runner makes direct, repeatable classifier calls through `evaluation/controlled_classifier.py`. It does **not** run OCR, process a document image, run the full pipeline, or measure `build_damage_map`. The existing synthetic card values in `tools/make_demo_docs.py` supply the fictional reference strings. Corrupted observations and synthetic damage conditions are authored in the evaluation manifest.

Evaluation-only `ground_truth` is read by the runner **after** `classify_field` returns. It is not passed to `Observation`, `MappedField`, `classify_field`, pipeline state, or production evidence. The harness API has no `ground_truth` parameter.

## Reproduction and artifacts

Run from the repository root:

```bash
.venv/bin/python tools/characterize_false_recovery.py
.venv/bin/python -m pytest -q tests/test_classifier.py tests/test_false_recovery_characterization.py
```

- `evaluation/false_recovery_cases.json` — 33 controlled input cases, including evaluation-only truth.
- `evaluation/false_recovery_results.json` — per-case outcomes generated by executing the current classifier; includes status, claim, pattern/validator findings, damage measurements, reasons, evidence, and version metadata.
- `tools/characterize_false_recovery.py` — deterministic result generator.
- `evaluation/controlled_classifier.py` — shared test/evaluation harness; it does not alter production classification.

The recorded code/classifier/pipeline version is `disasterdoc-0.1.0`, template `synthetic_id_v1`, repository revision `ea0d7e95cb36`. The worktree was already dirty from earlier work; source SHA-256 values for `src/classifier.py` and `src/config.py` are recorded in the JSON results.

## Case design

The corpus covers all five template fields: ID, date of birth, name, district, and address. It includes correct controls; single- and multiple-digit substitutions; common glyph substitutions; deletion; insertion; transposition; truncation with and without a marker; and incorrect values that satisfy the field's format pattern.

The single-digit ID substitution (`DX-48291` → `DX-48281`) is held constant across confidence inputs `0.40`, `0.60`, `0.80`, `0.94`, and `0.99`. At `0.94`, it is also tested with these direct `DamageMap` inputs:

| Synthetic profile | Measured field-zone obscuration | Measured adjacent obscuration |
|---|---:|---:|
| Clean | 0.000 | 0.000 |
| Rightmost 20% of field zone obscured | 0.200 | 0.000 |
| Rightmost 50% of field zone obscured | 0.500 | 0.000 |
| Adjacent probe obscured | 0.034 | 1.000 |

These masks isolate current classifier thresholds. They are not realistic image renders or detector outputs. Confidence values are injected controls, not OCR model scores and not probabilities of correctness.

Outcome labels are based on the evaluation-only comparison between ground truth and the classifier's completed result: `CORRECT_RECOVERY`, `FALSE_RECOVERY`, `CORRECT_ABSTENTION`, `UNNECESSARY_ABSTENTION`, and `OTHER_AMBIGUOUS`.

## Executed results

| Measure | Observed cases |
|---|---:|
| Controlled case rows | 33 |
| Correct recoveries | 5 |
| False recoveries | 16 |
| Correct abstentions | 12 |
| Unnecessary abstentions / other ambiguous outcomes | 0 |
| `RECOVERED` statuses | 21 |
| `PARTIAL` statuses | 12 |
| `UNRECOVERABLE` statuses | 0 |
| Format/length/token/truncation validator result: passed | 24 |
| Format/length/token/truncation validator result: rejected | 9 |

All five correct controls (one per field) were reported verbatim as `RECOVERED`. The 12 correct abstentions consisted of nine cases rejected by format/length/truncation checks, the `0.40` confidence case, the 50%-obscured field-zone case, and the adjacent-damage case. All abstentions kept `value=None`.

The 16 false recoveries were:

- **ID:** `DX-48281` instead of `DX-48291` at confidence inputs `0.60`, `0.80`, `0.94`, and `0.99`; the same substitution at `0.94` with 20% field-zone obscuration; multiple substitutions `DX-48071`; transposition `DX-42891`; and valid-format incorrect ID `QY-73156`.
- **DOB:** valid-shape but incorrect `14 08 1981`; and impossible calendar date `31 02 1991`.
- **Name:** `ANANYA RAQ` (O→Q) and plausible but wrong `ANANYA RAJ`.
- **District:** plausible but wrong `MYSURU`.
- **Address:** `42 LAKEVIEW 5TREET, WARD 7` (S→5); `42 LAKEV1EW STREET, WARD 7` (I→1); and `42 LAKEVIEW STREET, WARD 1`.

These are **counts of constructed rows**, not a false-recovery rate. Some rows deliberately repeat the same underlying substitution while varying one controlled input.

## Validator, confidence, damage, and evidence findings

### Format validation

Nine malformed observations were rejected and returned `PARTIAL` with no claimed value: ID `8→B`, ID `1→I`, deletion, insertion, unmarked truncation, marked truncation, DOB `1→I`, name `O→0`, and district `B→8`. The marked truncation also produced the classifier's truncation-marker reason.

Passing the existing field pattern did not establish truth. It allowed the single- and multiple-digit ID substitutions, ID transposition, valid-format incorrect ID, wrong date, wrong name/district/address, and the two address glyph confusions to be reported as `RECOVERED`. The DOB shape regex also accepted `31 02 1991`; it does not validate calendar dates. The nine `REJECTED` and 24 `PASSED` counts refer only to pattern/length/token/truncation reasons, not damage or confidence gates.

### Confidence

For the same wrong ID string, `0.40` was `PARTIAL` with a low-confidence reason and no value. The `0.60` case was `RECOVERED` with the `medium` heuristic bucket; `0.80`, `0.94`, and `0.99` were `RECOVERED` with the `high` heuristic bucket. Thus the existing `<0.50` gate abstained at `0.40` but did not establish correctness above the gate. The classifier's confidence bucket is heuristic and must not be read as a calibrated probability.

### Damage

With 20% of the field zone obscured, the damaged-area reading stayed below the current 0.35 limit and the wrong ID was still recovered. At 50% obscuration, the classifier returned `PARTIAL` and `value=None`. With only 0.034 overall zone obscuration but 1.000 obscuration in the adjacent probe, it also returned `PARTIAL` and `value=None`. The recorded reasons distinguish field-region damage from damage immediately after the observed text.

### Available reasons and evidence

Each result row retains the exact classifier reasons and its evidence observation (observed text, controlled confidence, and synthetic box). False recoveries generally carried the generic reason that usable OCR satisfied the expected pattern and the surrounding region was readable; the classifier had no independent truth signal for these cases. Damage and invalid-format abstentions retain their specific reason strings and measured damage boxes/ratios in the JSON output.

## Limitations and next phase

**Most important limitation:** these cases inject an OCR-like string directly into the classifier. They do not measure image-to-OCR errors, real OCR confidence, damage detection, or end-to-end pipeline false recoveries. The strings and reference values are synthetic and intentionally selected; the corpus is not representative, statistically powered, or suitable for estimating real-world error rates. One synthetic template and one controlled observation per case are used. No CER, calibration, statistical significance, or risk-coverage metric is claimed.

**Evidence-based next phase (proposed, not started):** run a small, targeted **image-level** evaluation using the existing synthetic document generator and masks, preserving reference text only in evaluation fixtures. First execute the unchanged OCR/pipeline on cases designed around the 16 accepted error patterns and matched correct controls; record the actual OCR strings, engine confidences, mapped evidence, and outcomes. Use those observations to decide whether any independent corroboration signal merits an offline comparison. Do not change production rules or choose a new engine/model until that image-level evidence demonstrates a specific benefit and its abstention trade-off. This phase stops before that work.
